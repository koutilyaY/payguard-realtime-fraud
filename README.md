# PayGuard

**Real-time payment-fraud detection on a streaming lakehouse — Kafka → Spark Structured Streaming → Delta Lake (bronze/silver/gold) → LightGBM → FastAPI + Streamlit.**

> **Heads-up — this is a self-contained demo on *synthetic* data.** There is no live production traffic behind it. The transaction stream is generated by a Faker-based producer, and the LightGBM model is trained on synthetically generated feature distributions. It exists to demonstrate an end-to-end streaming-ML architecture you can run locally, not to publish benchmark numbers. Any latency/accuracy figures you care about should be reproduced on your own data — see [Results](#results).

## TL;DR — run it locally

Requires Docker + Docker Compose, Python 3.9+, and a virtualenv at `.venv`.

```bash
# 0. Setup
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
cp config.yaml.example config.yaml      # then edit the Postgres password

# 1. Start infra (Kafka, Postgres, Redis, Prometheus/Grafana) and create topics
make up-all                              # also runs kafka-init after a 10s wait

# 2. Train the model FIRST — the stream loads mlruns/fraud_model.pkl on startup
make train

# 3. Start the streaming pipeline (bronze → silver → gold + sinks)
make stream                              # leave running

# 4. In another shell: produce synthetic transactions
make producer

# 5. In another shell: start the scoring/serving API on :8000
make api

# 6. Dashboard
cd streamlit_app && streamlit run app.py
```

> **Train before you stream.** `make stream` calls `_load_lgb_model()` and raises `FileNotFoundError` if `mlruns/fraud_model.pkl` is missing. Run `make train` on a fresh checkout before anything else.

Tear down with `make down-all`.

## The problem

Card fraud is a streaming problem with a hard latency budget: a decision that arrives after the authorization is worthless. Two common failure modes:

- **Batch scoring** flags fraud hours later — after the money is gone.
- **Static rule engines** are easy to reason about but drift quickly and over-flag legitimate customers.

PayGuard sketches a middle path: ingest transactions continuously, land them in an auditable medallion lakehouse, compute per-user windowed features, and score them with a gradient-boosted model whose outputs feed an online store and an analyst case queue — with a feedback loop so confirmed/false-positive labels can be folded back into retraining.

This repo is the *reference implementation* of that pipeline, wired end to end and runnable on a laptop.

## Architecture

```
                    ┌─────────────────┐
  synthetic txns →  │  Kafka  (:9092) │  topics: txns, txns_dead_letter, txns_alerts
  (Faker producer)  └────────┬────────┘
                             │  readStream (failOnDataLoss=false)
                             ▼
              ┌──────────────────────────────────┐
              │   Spark Structured Streaming      │
              │   parse JSON · schema/rule filter │
              └───────┬───────────────────┬───────┘
                 valid│                    │invalid
                      ▼                    ▼
     BRONZE  delta/bronze/txns_v1     DLQ  delta + Kafka (txns_dead_letter)
                      │
                      │  watermark 5m · dropDuplicates(event_id)
                      ▼
     SILVER  delta/silver/txns_clean_v1
                      │  groupBy(window 1m, user_id) → txn_cnt, amt_sum,
                      │                                 ip_risk_avg, chargeback_cnt
                      ▼
              ┌────────────────────┐
              │  LightGBM pandas_udf│  P(fraud) ∈ [0,1]  →  decision REVIEW / ALLOW
              └─────────┬──────────┘
                        ▼
     GOLD   user_risk_features_v1 (log) · user_risk_latest_v1 (upsert)
            fraud_kpis_daily_v1 · alerts_v1 · txns_alerts (Kafka)
                        │
          ┌─────────────┼───────────────────────────┐
          ▼             ▼                            ▼
   Redis (:6379)   Postgres (:5433)            Prometheus Pushgateway (:9091)
   user:{id}       cases table                 → Prometheus (:9090) → Grafana (:3000)
   risk snapshot   (analyst queue)
          │             │
          ▼             ▼
     FastAPI (:8000)  ── /decision/user/{id}, /label/case/{id}, /cases/labeled, /health
          │
          ▼
     Streamlit dashboard
```

**Why these pieces:** Kafka decouples ingestion from processing and absorbs bursts; Spark Structured Streaming gives windowed stateful aggregation with exactly-once checkpointing; the Delta medallion (bronze raw → silver deduped → gold serving) keeps every layer queryable and auditable; LightGBM is fast to train/score on tabular features; Redis serves the latest per-user risk for low-latency lookups while Postgres holds the durable analyst case queue.

## Fraud signals & rules

The model consumes **four windowed features** per user per 1-minute window (this is the entire feature set — see `src/ml/train_model.py` and `stream_fraud_pipeline.py`):

| Feature | Meaning |
|---|---|
| `txn_cnt` | transactions in the window (velocity) |
| `amt_sum` | total amount in the window |
| `ip_risk_avg` | mean IP risk score (0–1) across the window |
| `chargeback_cnt` | transactions with prior chargeback history |

Scoring is a single LightGBM `predict_proba`. A transaction window is marked **`REVIEW`** when `risk_score >= risk_threshold_alert` (default `0.7`, in `config.yaml`), otherwise **`ALLOW`**. Alongside the model score, human-readable reason tags are attached via SQL rules:

| Reason tag | Condition |
|---|---|
| `HIGH_IP_RISK` | `ip_risk_avg >= 0.8` |
| `HIGH_VELOCITY` | `txn_cnt >= 15` |
| `HIGH_AMOUNT` | `amt_sum >= 1500` |

Schema/business validation runs *before* scoring; rows failing it (bad currency/country/category, non-positive or oversized amount, out-of-range IP risk, nulls) are routed to the dead-letter Delta table and the `txns_dead_letter` topic instead of bronze.

## Results

This is a **synthetic-data demo**, so the README deliberately ships **no benchmark numbers**. Here is what is actually true and reproducible from the code:

- **Training data is generated, not collected.** `generate_synthetic_data()` builds 50,000 windowed feature rows at a 5% fraud rate (`src/ml/train_model.py`), encoding three fraud archetypes:
  - *Velocity* — high `txn_cnt` (15–50/min), moderate amounts, high IP risk.
  - *High-value* — low `txn_cnt`, large amounts ($500–$5,000), high IP risk.
  - *Account takeover* — moderate velocity/amounts with chargeback history.
- **The model is a LightGBM binary classifier** (200 estimators, depth 6, class-weighted) trained with an 80/20 stratified split and early stopping.
- **Metrics are logged to MLflow, not hard-coded here.** Training computes AUC-ROC, average precision, and precision/recall/F1 at a 0.70 threshold and logs them to the local MLflow store. Because the synthetic archetypes are well-separated by construction, these scores are optimistic and say little about real-world fraud — treat them as a smoke test that the pipeline learns the intended signal, not as a performance claim.

**To see real numbers, run `make train` and inspect the MLflow run** (printed run ID, or open the `mlruns/` file store). To evaluate honestly, retrain on your own labeled transactions via the analyst feedback loop below.

### Analyst feedback loop

REVIEW cases land in the Postgres `cases` table. Analysts label them through the API:

```bash
curl -X POST localhost:8000/label/case/<case_id> \
     -H 'content-type: application/json' \
     -d '{"label":"FRAUD","analyst_id":"alice"}'   # FRAUD | LEGIT | UNKNOWN
```

Then `make retrain` folds those labels into a new model; restart `make stream` to pick it up.

## Make targets, ports & endpoints

### Make targets

| Target | What it does |
|---|---|
| `make up-all` | Start Kafka + Postgres + Redis + monitoring, then `kafka-init` |
| `make down-all` | Stop all of the above |
| `make kafka-init` | Create the `txns`, `txns_dead_letter`, `txns_alerts` topics |
| `make train` | Train LightGBM on synthetic data → `mlruns/fraud_model.pkl` (**run before streaming**) |
| `make stream` | Run the Spark streaming pipeline (bronze→silver→gold + sinks) |
| `make producer` | Emit synthetic transactions to Kafka (~20/sec) |
| `make api` | Serve the FastAPI app on `:8000` via Uvicorn |
| `make dq_silver` | Run data-quality validation on the silver table |
| `make retrain` | Retrain using analyst labels from the `cases` table |
| `make up` / `make down` | Bring up/down only the core Kafka compose file |

Dashboard isn't a Make target: `cd streamlit_app && streamlit run app.py`.

### Service ports

| Service | Port |
|---|---|
| Kafka (host listener) | `9092` |
| Redis | `6379` |
| Postgres | `5433` (container `5432`) |
| FastAPI | `8000` |
| Prometheus | `9090` · Pushgateway `9091` |
| Grafana | `3000` (admin/admin) |
| cAdvisor `8082`, kafka-exporter `9308`, postgres-exporter `9187`, redis-exporter `9121` | |

### API endpoints (`src/serving/api.py`)

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Liveness + Redis connectivity |
| `GET` | `/decision/user/{user_id}` | Latest risk snapshot for a user (from Redis) |
| `POST` | `/label/case/{case_id}` | Submit analyst label (FRAUD/LEGIT/UNKNOWN) |
| `GET` | `/cases/labeled` | List labeled cases for retraining review |

> Note: there is **no synchronous `/score` endpoint**. Scoring happens inside the Spark stream; the API reads the resulting risk snapshots and manages the analyst feedback loop.

## Limitations & honest caveats

- **Synthetic everything.** Producer transactions and training data are generated; do not read MLflow metrics as real-world performance.
- **Local single-node Spark.** Tuned for a laptop (`spark.sql.shuffle.partitions=4`, 2g driver). Not a distributed deployment.
- **No auth/TLS on the API.** It's a demo server; add an auth layer before exposing it anywhere.
- **Feature set is intentionally small** (4 windowed features) to keep the streaming/training contract simple and aligned.
